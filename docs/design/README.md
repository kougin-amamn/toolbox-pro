# 設計書

アプリ(ツール・ランチャー)や共通の部品(`common/` のファイル)を新しく作る時は、**作る前にここへ設計書を書きます**。大きく作り変える時も、先に設計書を直します。

- 置き場所: `docs/design/<名前>.md`。名前はツールなら slug(`file-transfer.md`)、共通部品ならファイル名から(`log.md`)。
- 1つのアプリ・部品につき1ファイル。基本設計と詳細設計を、同じファイルの中で章に分けます(下の「型」)。
- 作った後: 実装で変わった所を設計書にも反映し、同じコミットに入れます。設計書と実装が食い違ったら、実装に合わせて設計書を直します。
- 公開しない: `docs/` は `.assetsignore` で公開サイトから外してあります。

## 書き方の決まり

### 基本設計と詳細設計

| 章 | 一般の呼び方 | 答える問い | 読む人 |
| --- | --- | --- | --- |
| 1 概要 | 企画・要件の要約 | 何のためか、誰がどこで使うか | 全員 |
| 2 基本設計 | 外部設計・方式設計 | 使う人から何が見えるか、どんな技術で作るか | 使う人・頼んだ人 |
| 3 詳細設計 | 内部設計・プログラム設計 | ファイル・関数・データをどう分けて作るか | 作る人・直す人 |
| 4 制限事項・試験 | 試験計画 | 何ができないか、何をどう確かめるか | 全員 |

- 基本設計には、作り方を変えても変わらない事を書きます(画面・操作・見た目・使う技術)。
- 詳細設計には、作り直すと変わる事を書きます(ファイル・関数の名前・データの形・処理の順番)。
- 迷ったら「使う人に見えるか」で分けます。見えるなら基本設計、見えないなら詳細設計です。

### 書く量(変更の大きさで決める)

| 変更の大きさ | 書く章 |
| --- | --- |
| 文言・見た目の小さな修正 | 書かない |
| 既存のアプリの機能追加 | その設計書の該当する節だけ直す(設計書が無ければ書かない) |
| 新しいツール(ファイルが画面と core くらい) | 1、2.1 要件と課題、2.2 外部仕様、2.4 処理方式の要点、4 |
| 新しいツール(ファイルが4つ以上、外部のライブラリ・サービスを使う) | 上に加え、2.3 デザイン(独自の画面がある時)、3 詳細設計 |
| 共通部品の新規・作り変え、ランチャー | 全部の章 |

中身が無い節は、見出しごと省きます(「なし」とは書かない)。

### 書き方

- 決めた事と、その理由を書きます。迷った案は「採らなかった案」に理由と一緒に残します。
- 並べる物(課題・操作・関数・設定値)は表にします。図は Mermaid です(GitHub でそのまま図になる)。
- 実機で確かめていない事は「要確認」と書きます。
- 冒頭に、状態と、作った日・直した日を1行で書きます。状態は「下書き / 確認中 / 決定 / 段 1a まで実装 / 実装済み / 置き換え(→ 新しい設計書)」のどれかです。一覧の「対象」にも、実装済み以外は状態を書きます。直した事の詳細は「実装の記録」に書きます。
- できないといけない事には要件番号(`R-01`)を付け、それを確かめる試験に試験番号(`T-01`)を付けます。試験の名前にも番号を入れ、どの要件を試しているか文字の検索で分かるようにします。
- 受け入れの条件は「〜の時、〜する」の形で書きます(1つの条件が、そのまま1つの試験になる)。
- 設計書に無い機能は作りません。足したくなったら「決めてほしいこと」に書きます。
- サイト全体に関わる決め事(ライブラリの版、配色、対応ブラウザなど)は、設計書ではなく、その決まりの文書(`site.md` `ui.md` など)に書き、設計書からはリンクします。
- 言葉は [`../glossary.md`](../glossary.md) に合わせます。新しい言葉はそこに足します。
- 3D の画面は、[`../design-3d.md`](../design-3d.md) の項目を確かめながら書きます。
- 見た目と名前は、それぞれ `docs/ui.md` と `docs/naming.md` に従います。設計書の中で、決まりと違う事を決めません。決まりを変えたい時は、決まりの文書を先に直します。
- 前からある設計書は、次に直す時にこの型へ移します(まとめて書き直しはしません)。

### AI と詰める進め方

設計書は、人と AI の対話で詰めます。

1. 質問は外側から内側へ進めます: 目的と範囲(やる事・やらない事) → 使う場面と操作の流れ → 見た目 → 失敗した時・端の条件 → 品質(速さ・端末) → 作り方 → 完成の条件(試験)。
2. AI は、答えで見た目・操作・データ・試験が変わる事だけを人に聞きます。1回に5問まで、選ぶ形で、おすすめの案と「なぜ大事か」を付けます。分かりきった事は聞きません。
3. 作り方のうち、決まりから導ける事・後から戻せる事は AI が決め、「AI が決めた事」に理由と一緒に残します。
4. 言葉で決めにくい事(見た目・手触り)は、試作を並べて選びます(`../design-3d.md` の「分からない所の決め方」)。
5. 人が確かめる所は3つです:
   - 基本設計(2章)ができた時: 外から見える事を決める。
   - 詳細設計(3章)と試験(4章)ができた時: 作り方と確かめ方を決める。
   - 作った後: 試験の結果と画面を添えて、実装の記録に書く。設計と作った物が合っているかを、作った AI とは別の AI に見比べさせます。
6. 設計の話し合いと、作る作業は、会話を分けると迷いが減ります(長い会話は `/compact` か、新しい会話にする)。

## 型

```markdown
# <名前> 設計書

状態: <下書き / 確認中 / 決定 / 段 1a まで実装 / 実装済み / 置き換え>。作成 <日付>、更新 <日付>。

## 1. 概要
何のためか、誰がどこで使うか、うまくいったと言える目安、前提(ブラウザ・https・外部サービス)。
- やらないこと: やれそうだが、あえて外す事と理由(「落ちない」のような当たり前の事は書かない)。

## 2. 基本設計

### 2.1 要件と課題
- 要件: できないといけない事(表。番号 `R-01`、受け入れの条件は「〜の時、〜する」)。
- 課題と方針: 作る前に洗い出した課題と、それぞれどう対応するか(表)。
- 採らなかった案: 案と、採らなかった理由(表)。

### 2.2 外部仕様
使う人から見える振る舞い。
- 画面の要素と、操作と結果(表)。
- 入力と出力(読むファイル・作るファイル・外へ送る物)。
- 覚えておく物(localStorage などに何を残すか。キー名は詳細設計)。
- 外とのやり取り: 使うブラウザの機能と許可(カメラ・センサー・クリップボードなど)と、許可を求める時、読むファイル・作るファイル、アドレスの指定(`?…` `#…`)。
- 失敗した時に、使う人に何が見えるか。
- ログに出す事(結果・警告・エラー)。

### 2.3 デザイン
画面の配置(スマホ縦・横・タブレット・パソコン)、大きさの決め方、アイコン、独自の部品の見た目。
画面の状態の一覧: 最初・空・読み込み中・失敗・許可されない・端末が対応しない、それぞれの見え方。
色は `docs/ui.md` のトークンだけを使い、ここでは使い分けだけを書く。

### 2.4 処理方式
どんな技術で作るか。
- 使うブラウザの機能と、外部のライブラリ・サービス(版と読み込み元)。
- ファイルの読み込み方式(普通のスクリプト / ES モジュール)、データの置き場所(`.json`)。
- 重さ・速さの考え方(描画、音、計算をどこで行うか)。
- 失敗の扱い(読めない時・許可されない時・端末が対応しない時)。
- 品質の目標: サイトの決まりと違う所だけ書く(速さ・通信量の上限、対応ブラウザ、使いやすさ、個人の情報の扱い)。

## 3. 詳細設計

### 3.1 プログラム構成
ファイルと役割(表、行数の目安)、依存の図(Mermaid)。

### 3.2 部品の仕様
各ファイルが公開する関数・約束(引数と返り値)、送るメッセージ。

### 3.3 データ設計
`.json` の形、localStorage のキーと中身、設定値と理由、上限。

### 3.4 処理の流れ
主な流れ(番号付きの手順か、Mermaid のシーケンス図)。

## 4. 制限事項と試験

### 4.1 制限事項
できない事、端末やブラウザによる違い、気になる点。

### 4.2 試験
試験の表(番号 `T-01`、確かめる要件 `R-01`、方法: Node の試験 `tests/core` / 画面の試験 smoke・scenarios / 実機)。
実機で確かめる事は、手順の形で書く。

## 5. 決めてほしいこと(ある時だけ)
1問ずつ、選ぶ案・おすすめ・なぜ大事か・いつまでに。
決まったら 2.1 に「採った案 / 採らなかった案(理由)」として移し、ここには「決定(日付)」の印だけ残す。

## 6. 実装の記録(段階で作る時・作り変えた時)
### <段 / 日付>
やった事、確かめた事(試験の結果)、残った事。
- 設計と違った事: 何を・なぜ・どの節を直したか。
- AI が決めた事: 人に聞かずに決めた事と理由。
```
